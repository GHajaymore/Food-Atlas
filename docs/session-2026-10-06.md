# 2026-10-06 — before launch

What changed today, why, and what is still waiting on Ajay. Everything below is
committed, built, deployed and checked on the live site.

## 1. Waiting proposals are visible to everyone

Nothing notified anyone when a proposal arrived: it landed in D1 and sat there until
somebody opened the admin queue with a token. Confirmations are the atlas's bottleneck —
three people who know the dish, and none so far — so the shortage is attention, not
submissions.

Email would mean another service and another secret, which is Ajay's call rather than
mine. The free half of the same job is now in: `src/data/pending.ts` counts the proposals
still short of their confirmations, and the masthead and the phone colophon show that
count beside *Confirm*. One request per visit, shared between the two through a
module-level promise, resolved after first paint; `loadProposals` already returns `[]` on
any failure, so a dead endpoint leaves the nav exactly as it was.

A bare number rather than a phrase: digits read the same in twelve languages, so no
catalogue falls behind. Proposals that already have their three are excluded — they wait
on a publish, not on a reader.

## 2. Two copy keys were being printed as words

Found by reading the live site rather than the code.

* Every card with an occasion on it read **"Vegan · mealSnack · mealCelebration"**.
* A record page's trace chips read **"containsAlcohol"** and **"dietDairy"**.

Both maps hold `keyof Copy`, and neither `mealLabel` nor `traceLabels` was looking the key
up — in every language, since the maps were written. Both now take the `Copy`, which makes
the mistake impossible rather than fixed, and `TRACE_LABELS` is typed as keys so the
compiler would have caught it. A regression test asserts the English words and that no
label in any catalogue still looks like a key.

The sweep covered every `keyof Copy` map in `src/domain`: shelves, continents, diet groups
and score dimensions all resolve through `copy[...]` and were clean.

## 3. Each screen is a page of its own

The export is one `index.html` and `_redirects` serves it for every unmatched path, so
`/atlas`, `/browse`, `/search`, `/how`, `/support` and `/privacy` all arrived with the same
title, the same description and no canonical of their own — while the sitemap listed them
as seven URLs. Measured: `document.title` was `WikiFoodia` on every one. To a crawler that
is seven duplicates of the home page.

`scripts/prerender-screens.mjs` now writes a file per screen with its own `<title>`,
description, Open Graph and Twitter title, `og:url` and canonical, copied from the finished
`index.html` so the body — and the CSP hash — are untouched. Pages matches `/atlas` to
`atlas.html` before the SPA fallback, exactly as `/dish/1` already resolved to
`dish/1.html`. The record counts in the descriptions are counted from the catalogue at
build time, not typed in.

`verify-prerender.mjs` fails the build if a screen in the sitemap has no file, has no title
of its own, shares a title with another, or does not point its canonical at itself. The
check reads the sitemap rather than a list of its own, so adding a screen there cannot
leave the gate behind.

`/propose` joins the sitemap at 0.6. `/proposals` stays out: it is a queue, and no
description of it would stay true.

## 4. Titles follow the route, and there is one canonical per page

A single-page app keeps its first title forever, so four tabs on four screens all read the
same thing. `src/domain/pageTitle.ts` sets the title from the route in the reader's own
language; the record page sets its own from the dish, matching what `prerender-records.mjs`
wrote into the HTML.

The injected canonical script wrote a tag for the current path unconditionally, so every
prerendered page ended up with two at runtime. It now defers to one already in the HTML,
and the screens write theirs at the top of the head where that guard can see it.

## 5. A page per country (same day, later)

The atlas is organised by place and had no address for a place. `/browse?country=Morocco`
is a query string: every one of them is served the same `index.html` with the same
canonical, which is why `prerender-records.mjs` deliberately refuses to link to them. So
atlas → country → dish stopped at the first step.

141 countries now have a page. `scripts/prerender-countries.mjs` writes the static half —
its own title, a description carrying that country's two numbers, a canonical, and its
records as real links, capped at 250 (it affects 10 countries). `app/country/[slug].tsx`
renders the same list in the same order once React boots, so the page does not reorganise
itself on arrival. Each record page now links out to its country, so a crawler can walk
dish → country → dish.

Only real countries get one. Levant, Mesoamerica, the Maghreb and the Ottoman Empire are
origins this catalogue records and none of them is a place with a flag — `catalogueMetrics`
already leaves them out of the headline count, and `/country/levant` would have put them
back in by the back door. Tapping one of those on the atlas keeps the older behaviour of
narrowing the feed.

Which countries get a page is decided once, in `scripts/lib/country-pages.mjs`, because
the sitemap has to make the same decision. `verify-prerender.mjs` fails the build if a
listed country has no file, lists no records, or does not point its canonical at itself,
and a test asserts every country in the shipped catalogue folds to a slug of its own — two
sharing one would mean a page silently claiming another country's records.

### One thing this got wrong first

The layout and the screens were both setting the browser title, and React runs a child's
effects *before* its parent's — so the layout's title landed last and clicking Japan left
the tab reading "WikiFoodia". The file had confidently commented the opposite. `titleFor`
now returns nothing for `/dish` and `/country`, and a test holds it.

Live now: 8 screens + 141 countries + 8,858 records in the sitemap, 5,177 record links
across the country pages, 665 tests passing.

## 6. Breadcrumbs, and a search box for the site

Two pieces of structured data, both of which only became honest once countries had pages.

**`BreadcrumbList` on all 8,858 record pages** — atlas → country → dish. Google shows this
trail in place of a bare URL under a result. The country step is dropped rather than
invented where that country has no page, so a record filed under the Levant or the Maghreb
gets a two-step trail, and the last step carries no `item`, which is how schema.org marks
the page you are standing on. In the app, the country step of the visible trail now opens
the country's page; the deeper steps stay filters, because a region has no page and
inventing one for two thousand of them would be two thousand pages holding a handful of
records each.

**One `WebSite` with a `SearchAction` on the home page**, which is what offers a search box
under a search result. It points at `/browse?q=`, not `/search`: `browse.tsx` parses a
query out of the URL and the search screen keeps its query in app state, so `/search?q=…`
would be a promise the site does not keep. `inject-website.mjs` runs *after* the three
prerenders, so the entity is on the home page and not copied onto 9,000 others.

### What this broke, and how it was caught

The build gate read only the *first* JSON-LD block on a page and assumed it was a Recipe,
so the moment a second block existed it reported 8,858 recipes with no method — the right
failure for the wrong reason. It now reads every block by `@type`, and checks a trail has
at least two steps, ends without a link, and carries real URLs. 8,858 pages with a
breadcrumb, verified live: both blocks parse in the browser.

## 7. An accessibility sweep, and what it turned up instead

Audited the live site rather than the code: every visible image checked for alt text, every
control for an accessible name, headings for order, every leaf text node for contrast
against its actual background, and the keyboard path into the page.

The accessibility result is clean. On the record page, the country page and the feed: no
image without alt text, no control without a name, a sensible heading order (one H1 and
descriptive H2s), no text under 12px, and one apparent contrast failure that was my own
measurement error — the skip link is clipped to 1×1 until focused, and the audit measured
it clipped. Its `:focus` rule is in the shipped stylesheet and restores full size and an
accent background. Lesson for the next audit: skip clipped and off-screen nodes, or the
report is wrong in the one direction that wastes time.

What the sweep actually found was a copy fault, by reading the headings in order:

> 🟡 Traditional Variation · 27/100 Authenticity confidence
> **Authentic Version**

**"Authentic Version" headed the method and ingredients on every documented record that
was not a Cookbook adaptation** — and since no record in this atlas is currently Authentic,
that was nearly every documented record. "Why is this considered authentic?" headed the
explanation underneath it on the same condition. The adaptation case had been handled, and
its comment states the rule exactly: *the heading has to agree with the badge*. It only
half held.

Now it holds for every badge: the published recipe where it is one, the authentic version
only where the badge says authentic, and otherwise **"The version recorded here"** — which
is what the sources actually gave us, with the badge above saying how far it has been
checked. The explanation falls back to "What this record is", a string the page already
uses for the same passage on an empty record. The new line is hand-written in all twelve
languages.

Verified live: `/dish/1` carries no authenticity claim anywhere in its text, and the home
page's stat tiles still read `0 AUTHENTIC`, which is the same fact stated the same way.

## 8. A region names a place, not a people

Reading the empty record for a Goan dish, in order, as a reader meets it:

> India › **Goan** · Also from **Goan** · 3 more people connected to **Goan**

"Goan" is not a place. Behind it: "Ghana › Angolan", "Indonesia › Belizean", "India ›
Emirati", "South Africa › South African", "United Kingdom › Ancient Iran" — about a
hundred records whose place trail named a nationality, a people or a cuisine. The trail is
the one thing on a record the atlas asks a reader to confirm.

The defence that existed was a hand-written list of nine demonyms, so it covered what
somebody had seen and nothing else. It is now worked out: a handful of ways English builds
a demonym, undone in turn, and the label is dropped when any stem lands on a country the
atlas knows — Angolan → Angola, Belizean → Belize, Kuwaiti → Kuwait, South African → South
Africa. Dropped whether or not it is the record's own country, because "Ghana › Ghanaian"
says the country twice.

Conservative by construction: a stem counts only when it is a country outright, so Fujian,
Busan, Sichuan, Kalimantan, Rajasthan and Kurdistan are untouched — and a test holds
exactly that list, because over-reaching here would silently delete real places. The
adjectives naming a *region* can never be reached this way, so sixteen are translated by
name: Goan → Goa, Punjabi → Punjab, Okinawan → Okinawa, Sindhi → Sindh.

Tibetan is dropped rather than translated, for the same reason as Macanese: the atlas files
Tibet as a country of its own, so "China › Tibet" would be one country presented as a
region of another. The existing invariant test caught that within a minute of my writing
it, which is what it is for.

## 9. Two claims on the privacy page, and one on the page that makes the argument

**/how** said three of the six dimensions "cannot be answered by any document ever written"
and then quoted a ceiling only a document can reach. The code settles it: `technique =
registerMethod || communityMethod`, so a heritage register that publishes the production
method it protects *does* answer technique — the narrow, deliberate exception argued for in
`assess.ts`. The page now names it, and the dimension table reads "people, or a register"
instead of "only people".

Both ceilings are computed by calling `assess` with perfect documentary evidence and no
people at all: **35** on ordinary published sources, **43** where such a register exists.
It was `const DOCUMENTED_CEILING = 43` with a comment pointing at `assess.ts` — a claim
about code that nothing checked, on the page that invites a reader to check the arithmetic.

**/privacy** said the chosen language "is remembered inside your own browser and never sent
anywhere". Measured: picking Spanish fetches `/data/copy/es.json`, so the request names the
language. It also said two cookies; there is a third for ten minutes during sign-in, which
checks that Google's reply came back to the request that started it. Both corrected. The
privacy page is English-only by design, so neither needed translating.

Also: "Nobody has yet. The badge requires 3, so **3 more** people connected to Goa would
meet it." More than nobody is not a number; with no confirmations the count is now plain,
in all twelve languages.

## 10. The home page said submissions were closed. They are open.

Under the main ask on the front page:

> Submissions are not open yet — there is nowhere to send them.

`/propose` has been posting to this app's own API since proposals shipped. The line is
gated on `canContribute()` and `canConfirm()` — two flags that ask about external form URLs
nobody ever set — and knew nothing about `canPropose()`, which is true. So the front page
of a site whose proposal form works told every visitor it did not.

- The home page counts `/propose` now, the line is gone, and "Record a dish you know" goes
  to the form that posts.
- `/contribute`, the older teaching flow, ended on the same sentence *after* walking a
  reader through typing out their grandmother's dish. It now ends with a button into
  `/propose`, carrying what they typed.
- `/propose` reads the `dish` and `place` it is handed. Those parameters have been in the
  URL since the record pages began asking for a method, and the one form that actually
  posts was ignoring both — so the last step of the funnel asked for the name again.

### The one left open, and why

**Confirming an existing record still has nowhere to go.** `canConfirm()` is false, and the
record page's "Yes — it's from here" leads into the contribute flow, which now ends at
*Propose this dish* — right for a record with nothing written down, a blunt instrument for
one that has a method and wants a second voice on it.

Closing it properly means an endpoint and a table of confirmations against catalogue
records, which is a migration on the production database and a decision about what a
confirmation on an imported record *means*. That is Ajay's call, not something to apply to
his D1 unattended. It is the single highest-value thing left: the atlas's whole premise is
that people from a place close the gap documents cannot, and today there is no door for
them to come through on a record that already exists.

## 11. Search ordering, English articles, and a performance measurement

**Search put the wrong record first.** Measured on the shipped catalogue: "pierogi"
returned *Momo* ahead of *Pierogi*. A Polish local name on the momo record mentions
pierogi; Pierogi itself is unscored; relevance had two tiers — named for the query, or
merely containing it — so inside the top tier evidence ordering sent the record with that
exact name to the bottom of its own result. "kimchi" sat behind Dubu-kimchi, "sushi" behind
Sushi pizza, "tacos" behind French tacos.

A third tier: a record whose name, in any language, folds to exactly what was typed. That
is not a finer guess at how well a name matches — which `queries.ts` deliberately refuses —
it is the case where there is nothing to guess. Pierogi, kimchi, momo, sushi, tacos,
biryani and ghee now each lead with the record of that name, and evidence still orders
every tier.

Still true and left alone: "goa" leads with goat dishes, because the term matching is
substring-based and no record is *named* Goa. The country page now exists for that reader.

**"prepared in United Kingdom".** Seven places put a country name inside a sentence, and a
handful of English names are ungrammatical without an article — about 1,400 records sit
under one. `placeInSentence` adds it where a name goes into prose and nowhere else: a
heading, a breadcrumb and a card's place line are labels. English only, by construction,
and a test holds that every other language is untouched.

**Performance, measured on the live home page** (fast connection, so these are transfer
sizes rather than timings): one JS bundle at 1.44 MB compressed (7.4 MB decoded), and 4.19
MB of JSON across eight files, of which roughly 2.1 MB is needed before the feed can
render — the rest is the deferred prose from the September pass. 67 requests, 50 of them
cross-origin photographs.

The remaining lever is architectural rather than a tweak: every reader downloads the whole
catalogue because the app holds it in memory and filters locally, which is also why search,
browse and the atlas work with no server. Splitting the data by country or by shelf would
cut the first load several-fold and is a real piece of work, not a build-step change. Worth
doing before any campaign that brings phone readers in volume; not worth doing unattended.

## 12. Confirmations on records that already exist

The feature §10 left open, built to `docs/confirmations-api.md` — which specified it
before there was a server. Three of the six dimensions a record is scored on cannot be
answered by any document; until now the only way anybody could answer them was to confirm
a *proposal*, so the 17,358 records already in the atlas had no route to the badge, and
the record page's own ask led into the submission flow.

What shipped:

- **`migrations/0009_record_confirmations.sql`** — `record_confirmation`, beside
  `proposal_confirmation` from 0001. Two unique indexes rather than one: one published
  confirmation per person per record, **and** one per account where there is an account.
  Clearing cookies issues a new person id, and that must not become a second *counted*
  confirmation, because a counted one is precisely one tied to an account.
- **`GET /api/confirmations`** returns exactly `ConfirmationIndex`, because `catalogue.ts`
  hands the body straight to `buildCatalogue` and `assess` scores it. `person_id` and
  `account_id` never appear in a response; `verified` says somebody was signed in and
  nothing about which account.
- **`POST /api/confirmations`** — 422 with nothing said, 409 when this person has already
  confirmed this record, 503 while the table is missing.
- **The record page shows what people said** — name, stated connection, and the sentence
  itself. That is the design's oldest rule ("shown, not counted") and the one part of it
  the record page never had. The form is the same `ConfirmForm` the proposals queue uses,
  because it is the same act against the same threshold.
- **Disagreement is not a confirmation.** "No — it's from somewhere else" still goes to
  the submission flow rather than adding a row to the count that moves a badge.

### Two things that keep it honest before the schema exists

The migration is applied by hand against production, so the code had to behave before it
runs: reads answer `{}` and every record is scored as one nobody has confirmed, which is
true. And because an empty index and a missing table look identical to the client, the read
reports which it is in an `X-Confirmations` header; the record page offers the form only
when the server says the table is there. It starts closed — the direction that never wastes
the one reader who knows the dish.

Identity is a second signed cookie, `wf_cid`, scoped to `/api/confirmations`. Not the
proposals cookie widened to `/api`: that would ride along with the analytics beacon, and
the promise that no page view can be joined to a person is worth more than a cookie. The
crypto moved to `functions/api/_identity.ts` so there is one copy of it. The privacy page
now says there are three cookies and why two of them exist.
