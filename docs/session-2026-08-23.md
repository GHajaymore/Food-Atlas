## The thing to know first

**Nothing built today exists for a reader until the site is deployed.** Proposals,
confirmations, sign-in, the admin console, moderation, analytics and the refresh queue
all run against a local D1 and nothing else. `docs/deploy.md` has the steps; they need

## What changed, in the order it mattered

### The architecture plan was wrong, and measuring proved it

`docs/architecture.md` led with "14.7 MB before first paint" and built stage 0 on it.
That number is real and is a **dev-server artefact** — Metro sends no `Content-Encoding`,
confirmed by comparing `transferSize` against `decodedBodySize` in the page. Under brotli
the same payload is **2.92 MB**, and every static host compresses by default.

Two more measurements reversed the priorities:

```
  parse of the whole catalogue    133 ms   never the cost
  JS heap once built            122.3 MB   always was the cost
  built catalogue serialised      35.83 MB   vs 15.68 MB of sources
```

That last one kills the obvious fix: shipping pre-built records would *double* the
download. Expanding in the client is the compression. Stage 0 survives as a memory fix,
not a bandwidth one, and the doc now says so.

### A database, narrowly

The same doc argued against one because "the content is static; only the confirmations
are not". True until proposals — readers change the content now. Resolved the narrow way:
**D1 holds what readers write, files keep the 18,008 records that change when a script
runs.**

Everything was verified against a local D1 by trying to break it, not by reasoning:
propose 201, self-confirm 403, second confirmation 409, duplicate dish 409, decline
without a token 401.

### Sign-in, because "3 confirmations" did not mean three people

Ajay asked how we would know the same person was not confirming twice under two names.
The honest answer was that we could not — identity was a signed cookie, which stops a
double-tap and does not stop three private windows.

He approved the recommendation, which was deliberately **not** a login wall:

- Anonymous confirmations are still made, stored and **displayed**. Requiring an account
  to speak would exclude the grandmother in Kozhikode.
- Only signed-in ones are **counted**. `validationsOf` filters on `verified`, and
  `confirmedLocally` with it.
- What is stored is a salted hash of the Google subject. No user table, no email, no
  name; scope is `openid` alone.

The front page's "no accounts" had to go with it — it now says an account is needed only
to confirm a dish, never to read one.

### The website

Ajay, repeatedly and correctly: *"it still behaves like an app"*, *"things rendering
behind each other is not a right design"*. He was right about the cause. Every
`wide ? a : b` put a layout decision inside a component that should not have one, and the
interactions between a dozen of them were unholdable — the language dropdown painting
behind the page was that debt coming due.

So layout moved into components that own it and nothing else: `RecordColumns`,
`SearchColumns`, `layout.ts`. Neither the content nor the screen knows the window width.

And the atlas became **linkable**, which is most of what separates a website from an app:
`browse.ts` + `FacetLink` + `/browse`. Every country, region and ingredient on a record
opens the list it belongs to, at a URL that can be shared. No new query engine — `feedFor`
and `searchResults` already ran all of it.

### Searching by what is in your kitchen

`pantry.ts` — "I have chicken, rice, coconut" ranks Hyderabad Biryani first. Worth
recording *why* this works when the ingredient facet did not: **listing is hard, matching
is easy.** Offering 27,036 ingredient strings as options is impossible; finding "chicken"
inside "1 whole chicken, jointed" is trivial.

Restricted to main ingredients at Ajay's instruction — nobody plans a meal around cumin.
`staples.ts` is the fifty-three-term vocabulary, curated rather than counted because
counting produces salt, sugar and water.

## The mistakes, and what they teach

**Geometry is not visibility.** I told Ajay the language selector was fixed twice, having
checked with `getBoundingClientRect` and `innerText` — both of which report a covered
element as present and correct. The list was rendering *behind* the page.
`elementFromPoint` in the middle of it returned "How it gets authenticated". Hit-test,
don't measure.

**Right vocabulary, wrong subject — twice more.** A French brioche matched "paneer"
because *"se dépanner"* contains "panner". And a keyword sweep for drinks would have
deleted an apple (Reinette de Champagne), a cheese (Formaggio del Grappa) and a pasta
(Penne alla vodka). This is the failure this codebase produces more than any other.

**The sign was backwards on the one screen that must be trusted.** The admin
blast-radius counter reported "53 records would stop being Authentic" when *lowering* a
threshold. It modelled only the promotion branch; those 53 arrived through the heritage
branch, which never reads the score.

**A number asserted rather than read.** A commit message claimed 428 tests when the real
figure was 407. Corrected in the following commit.

**Writing to a generated file.** `check-sources.mjs` first wrote revisions to
`public/data`, which `compact-data.mjs` regenerates — every run would have reported
success and lost the data at the next compaction.

**Unchecked reported as unchanged.** The same script printed "0 have been edited" for a
record it had skipped for want of a baseline.

## Traps this codebase sets

- **Metro does not see new files on Windows.** A `share is not defined` crash on the
  front page was a stale bundle, not a code fault. Restart the dev server.
- **Backticks inside `node -e` get eaten by the shell.** It has mangled a comment and a
  SQL string today. Use the Edit tool for anything containing backticks.
- **`public/data` is generated.** `src/data` is the source of truth.
- **`minWidth: 0` on every flex child that holds text**, or one long ingredient name
  pushes a column past its share and spills the layout.
- **A z-index needs a `position`** — and `TopBar` renders before `<Stack>`, so it needs
  its own stacking context or the page paints over it.
