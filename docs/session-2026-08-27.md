# 2026-08-27 — why translation was never actually happening

Ajay reported it twice, the same way both times: *"there are still translation issues in
some sections. ex. Kozhikode Halwa."* A Japanese page, an English record, no error.

Four faults in a row, each of which hid the next. Worth writing down because none of them
raised anything — the app was silent at every stage, which is why it survived a full
translation audit that only looked at output.

## 1. The endpoint was never called

`EXPO_PUBLIC_TRANSLATION_ENDPOINT` was unset, so `RemoteTranslationProvider` defaulted to
`''`, `isConfigured()` returned false, and `canTranslate()` said no. Workers AI was on, the
function answered correctly to curl, the record screen asked for a translation on mount —
and nothing was requested.

**What proved it:** the D1 `translation` table was empty and `translation_day.spent` was
sitting at exactly 5, the number of calls I had made by hand. Not "some translations
failed". *None had ever been asked for.*

Default is now the app's own `/api/translate`, the same shape `EXPO_PUBLIC_DATA_URL` uses.

## 2. The record language was hard-coded

`useTranslations` declared `language: 'en'`, entirely separate state from
`useLocale().locale`. Picking Japanese translated the chrome; the record language stayed
English. And Kozhikode Halwa *is* written in English, so:

```ts
if (dish.sourceLanguage === language) return;   // 'en' === 'en'
```

returned before any fetch. The record language now follows the app's until the reader picks
one of their own — `languageChosen`, set by `setLanguage`, keeps `LanguageBar` an explicit
override. Wired with `useLocale.subscribe` rather than into `setLocale`, so `i18n` does not
need to know a translation store exists.

## 3. The translation arrived, and was thrown away

With 1 and 2 fixed the model returned a complete, correct Japanese translation — and
`assertPreserved` rejected it.

The number check compared the whole record's digits as one bag. The method says "over 2–4
hours" in step 3; the translation also named the duration in the summary. `2,4` met
`2,2,4,4` and the reader was told the numbers had been altered. They had not.

Now per step, index-aligned. **This is stricter, not looser** — the bag could not see a
number move *between* steps, so a translation that soaked the rice for four hours and
thickened it overnight used to pass. The summary is held to its own rule: it may not lose a
number it had, and may not introduce one that is nowhere in the record.

## 4. The rejection was printed in English

`errors` held whatever the provider threw, rendered verbatim. So a reader on a Japanese page
was shown *"Translation altered the numbers in the method."* — one of the mixed-language
sections Ajay was reporting. It was one. Just not in the record.

`TranslationFailure` is now `{kind:'refused'}` or `{kind:'service', text}`. A broken
preservation rule (`PreservationError`) is a diagnostic: logged in English, shown as
`copy.translationRefused` in the reader's language. The endpoint's own refusals — a daily
limit reached — are still shown as written, because those are addressed to a reader and say
something they can act on.

## And a fifth, found while verifying

The French page read *"il est donc affiché en English"* and *"sous-titres en French"*. The
sentences were translated; the language names inside them came from the static English label
list.

`Copy` now carries `locale`, stamped by `copyFor` so no catalogue declares it, and the five
prose builders in `language.ts` and `translate.ts` call `languageNameIn(code, copy.locale)`.
Reads "en malayalam", "en français". The prompt in `translationProvider` still uses the
English name deliberately — the model reads English instructions.

## Verified on production

- `/dish/1` in Japanese: summary and steps in Japanese, no English prose, no English error.
- `/dish/1` in French, cold: the app's own `POST /api/translate` fired, a D1 row was written,
  and the day's spend went 6 → 7. This is the one that matters — it proves the app, not curl,
  drives the chain.
- Ingredients and equipment stay in Latin script. That is by construction, not a gap:
  `preservedTerms` sends them as a do-not-translate list and `assertPreserved` enforces it.

## Still open

- **Writes remain parked read-only.** Waiting on Ajay's `IDENTITY_SECRET`.
- **The 8B model leaves partial translations** — Devanagari has appeared inside French
  output. A larger model costs money, so it is Ajay's call, not mine.
- `admin.tsx`'s 32 English strings are deliberately exempt.
- Two items still unverified in a real browser: scroll reveal, loading skeleton.

# Same day, second pass — what the data was hiding

## Mobile is no longer the problem it was

The old research recorded the first photograph at **1,167px on a 375×812 phone**, 1.44
screens of chrome before anything to look at. Measured again today: **359px, 0.44
screens**, on a page 4.9 screens tall. The mobile pass landed. Motion is present too —
1,048 elements carry a transition, against the "no motion at all" the research recorded.

## Scroll reveal cannot be verified from here, and that is the honest answer

`data-reveal` reported all five shelves already `in`, which looks like the reveal firing
for everything at once. It is not. The pane's tab reports `visibilityState: 'hidden'` and
`requestAnimationFrame` never runs in it — 0 frames in 600ms — so every reading is an
artifact of a background tab rather than a measurement of the feature. Fronting the tab
does not help; the terminal is the foreground application.

Left recorded as unverified rather than claimed. `theme/reveal.ts` is built so its worst
case is a section sitting ten pixels low, which is the right thing to be relaxed about.

## A word may be in any script. It may not be in two.

Eight strings had a single letter from the wrong alphabet standing in for its lookalike.
All eight were invisible on screen and none could be searched for:

| String | The intruder |
|---|---|
| `Georgian сheese` | Cyrillic с for Latin c |
| `dolmadakiа` | Cyrillic а ending a **name** |
| `Νευροκοπίοu` | Latin u ending a Greek PGI name |
| `Weiβburgunder` | Greek beta for German eszett |
| `Jујуба` | Latin J starting a Serbian word |
| `Mυτιλήνη` | Latin M starting Mytilene |
| `Maнов мед от Странджа` | Latin Ma starting a Bulgarian name |
| `Bulgarsko kiselo mlуako` | Cyrillic у inside a transliteration |

Note the last one runs the other way — it sits in a Latin transliteration, so the
Cyrillic letter is the intruder. "Correcting" it to Cyrillic would have been the
tidy-looking wrong answer, and a rule that only knew one direction would have made it.

Three were found by hand; the other five by the invariant, including one in `gi.json`
which no test had ever read as text. **Write the check before believing the count.**

The rule is restricted to Latin against Cyrillic and Greek on purpose: those three
separate words with spaces, so one token holding two of them is a defect. CJK, kana and
Thai do not, so `Thukpa一词在藏语中` is a single token by the same measure and is correct
prose. A looser rule would have shipped a false alarm into the suite.

## A false alarm worth recording

A first scan claimed **26 records with foreign prose claiming to be English**. That was
wrong: it tested for the *presence* of a non-Latin character, and nearly all 26 were
English prose correctly citing a native term — `bap was made using gamasot (가마솥…)` —
which is what the authenticity rules ask for. Measured as a *proportion* of letters, the
real count is **zero**. The enrich script had done its job; 1,244 of 1,270 foreign-prose
records declare their language, and the rest are English.

I nearly reported 26 bugs that did not exist. Presence is not proportion.

## Partial translations are now refused

`assertTargetScript` rejects a translation containing a script that is in neither the
target language nor the source record — the "Devanagari inside French" failure. Allowed:
Latin always (every preserved term is Latin), the target's own scripts, and anything the
original already contained, so a record that quotes a Malayalam term may go on quoting
it. Under three characters it stays quiet, because one stray character is noise and
refusing a whole translation over it is worse than showing it.

Could not be reproduced on demand — both cached translations are clean (ja is Han+Kana,
fr is pure Latin) — so it is a guard against an observed weakness, not a fix for a live
repro. Said plainly rather than dressed up.

## Checked and found correct, so left alone

- **`/api/settings` returns `{}`.** The `setting` table is empty and the client falls
  back to compiled defaults. Documented behaviour, not a fault.
- **The sign-in plan is complete.** `/admin` is linked from `/support`, `SessionControl`
  is in `TopBar`, `SiteNav` and `SiteFooter`, and `/how` has its accounts section.

## The one thing still blocking Ajay's own report

`GET /api/auth/me` returns `{"available":false}` in production, so **no sign-in control
renders anywhere** — which is why he still cannot see the login. The code is right and
the omission is deliberate: a control that goes nowhere is worse than none. It needs
`GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, which are his to create on his own Google
account, alongside the `IDENTITY_SECRET` still outstanding.

# Third pass — what the template stripper had been eating

Both importers deleted every `{{template}}` whole. Most are citations and deserve it.
Two kinds are not:

| Template | What it was | What the reader got |
|---|---|---|
| `{{convert\|375\|F\|C}}` | an oven temperature | "Preheat the oven to ." |
| `{{convert\|39\|C}}` | a curd temperature | "over a wood fire to about ." |
| `{{lang\|it\|…}}` | a cheese's name | "generally known as ." |

**An oven temperature is the one number in a step nobody can infer.** A cook can judge
"until golden"; nobody can judge 175°C against 220°C. And every one of these still read
as a sentence, so nothing looked broken enough to check.

87 records repaired: 24 catalogue, 12 cuisines, 51 English recipes.

## Three faults that were discarding whole passages

Each of these threw away prose entirely, so the record showed *no* method rather than a
damaged one — which is why they never looked like bugs:

1. **Templates stripped with a regex.** `/\{\{[^}]*\}\}/` cannot see a template inside a
   template, so it stopped at the first `}}` and left a bare one behind. Prose holding a
   stray brace is then rejected whole. Parmesan had lost a 3,277-character production
   section this way.
2. **Image links matched with a negated class.** A caption containing a link of its own
   ended the match early and left a pipe behind. Same outcome.
3. **`<gallery>` blocks.** Files are listed bare, one per line, no brackets to count. The
   tags came off and the filenames stayed behind as prose.

All three are counted now rather than pattern-matched. The lesson repeats: *a regex
cannot parse a nested structure, and the failure is silent because the guard downstream
looks like it is working.*

## The accident, recorded because it was mine

I checked whether `ingest-wikibooks.mjs` guarded its `main()` by grepping for
`import.meta.url`. It matched — on line 34, an unrelated use. `main()` was **not**
guarded, so importing `section()` started a full cookbook ingest that rewrote
`src/data/cookbook.json` underneath the repair pass reading it. Caught it at 6,980 rows
against an expected 6,979 and restored from git; the enrichment fields were intact.

Two things to keep from that: **grep matching is not proof of the thing you inferred**,
and an import must never have a side effect that large. Both ingest scripts are guarded
now.

## Two false trails, both worth remembering

- **"Rate limiting."** 190 of 256 recipes came back unrepairable, and a diagnostic run
  hit *"You are making too many requests to the API."* I added throttling and backoff.
  The number did not move. The real cause was that the cookbook is **five wikis** —
  `pt.wikibooks.org/Livro de receitas`, `es.wikibooks.org/Artes culinarias` — and the
  repair asked `en.wikibooks.org` for every title. The throttling was still worth
  keeping; it just was not the bug. *A plausible cause that reproduces is still not the
  cause.*
- **"371 damaged strings."** The first count included every field and several gaps per
  string. The real number of damaged summaries was 27.

## Deliberately not fixed, and counted rather than hidden

- **190 recipes** on the it/fr/de/pt/es Wikibooks. They name a method differently
  (Preparazione, Préparation, Zubereitung, Modo de preparo) and the Spanish book has no
  headings at all — its recipes are the parameters of a `{{Datos de receta}}` template.
  They need `ingest-cookbooks-multilingual.mjs`'s extractor, not this one.
- **15 English recipes** whose value is missing on Wikibooks itself.
- **9,219 records with no `prepSummary` at all.** Some fraction were lost to the three
  faults above and would come back from a re-enrichment — that is ~460 API requests and
  a large diff, so it is a decision rather than a cleanup.

## Where the invariant draws its line

Zero for catalogue, cuisines, gi and unesco. A ceiling for the cookbook that can only
fall — if a change repairs more, the test fails and the ceiling comes down with it.

It checks only the unambiguous shape: a space before a comma or full stop. The collapsed
form ("Preheat an oven to.") is what the repair passes hunt for, but it cannot be an
invariant — *"used to rub the bread with."* is a whole sentence, and a test calling that
a defect would be wrong five times in the catalogue alone.

# Fourth pass — the other five cookbooks

The previous pass reported **190 recipes as unrepairable**. They were not. The cookbook is
drawn from six Wikibooks — en, it, fr, de, pt, es — and the repair asked
`en.wikibooks.org` for every title. A Portuguese page answers "missing" there, which the
loop counted as a skip, so the number read as a fact about Wikibooks rather than a bug in
the client. **The language was in each row's own URL the whole time.**

211 recipes mended across all six, steps and ingredients alike:

| | before | after |
|---|---|---|
| es | "Machacamos el ajo en un , con la sal" | "…en un **almirez**, con la sal" |
| es | "En una , ponemos aceite" | "En una **olla**, ponemos aceite" |
| en | "Preheat the oven to ." | "Preheat the oven to **375 °F**." |

Each book is read the way it writes a method, through the extractor that first wrote it:
headed sections for en/it/fr/de/pt, and for Spanish the parameters of a
`{{Datos de receta}}` template, because that book has no headings at all.

Three causes turned out to hide behind one symptom, which is why "0 repaired" was the
first result after the language fix:

- **es** — `{{ute|almirez}}` and `{{ing|Agua}}`, the book's own utensil and ingredient
  templates. Real losses, 113 records.
- **fr, it** — stray spaces in the source wikitext (`"le pain plat (Pide) ."`). Nothing
  missing; normalised rather than repaired.
- **en** — `{{convert}}`, already handled.

## Two faults of mine, both caught by tests

1. **Order.** I put the rendering *after* the rule that strips a trailing `}}`, so a
   template at the end of a line arrived unclosed and matched nothing — `{{ing|Agua`
   reached the reader as raw markup. The catalogue's own invariant caught it. *A pipeline
   step that removes structure must run after the steps that read it.*
2. **Accepting markup.** The repair then took lines still holding `{{rec|…}}` and a stray
   `|15px` off an image parameter. A repair that trades a missing word for wikitext is not
   a repair. A re-derived list holding a brace or a pipe is now refused **whole** — the
   same rule the English ingest already applied — and ten recipes are declined on that
   ground, keeping a gap that is already recorded.

Both were found by the suite rather than by me reading output, which is the argument for
having written the invariant first.

22 wounds across the two cookbook files, every one either damaged on Wikibooks itself or
refused above. Ceilings in `plumbing.test.ts` can only fall.

Still open from the third pass: **9,219 records with no `prepSummary` at all**. Some
fraction were lost to the nested-template and gallery faults and would come back from a
re-enrichment — ~460 API requests and a large diff, so it is Ajay's call rather than a

# Fifth pass — the re-enrichment, and the correction it produced

I expected the 9,219 records with no method to be largely records the three stripper
faults had robbed. **They were not.** The pass recovered 36 of 3,506 — 1% — and the
headline is the correction, not the gain.

Measured *before* running, on 120 records sampled evenly rather than off the head of the
file: **119 had no preparation, production or method heading at all.** The single
exception had one, and it is a bullet list — 49 characters once list lines are dropped,
correctly refused by the 120-character floor. There was no fourth fault to find.

5,713 of the 9,219 have no URL to re-read at all: a GI or PAT register entry is a name, a
place and a legal reference, with no article behind it.

36 records did gain a real method — chimole, rødgrød, Brie de Melun, German baked apples —
so the run was worth making. But the estimate that motivated it was wrong, and the reason
it was cheap to discover is that the sample cost 6 requests and the full run cost 176.

**Sample before you commit to the run, and spread the sample.** The first-60 sample gave
1/120 too, but only by luck: these files are ordered, and the head is not typical.

## And nine names nobody could type

"Fave bianche e  cicorie PAT", "Tagliatelle  all'acciaccata PAT" — a doubled space inside
the name. Invisible on screen, because HTML collapses the run. But a name is typed in
order to be found, and an exact-match search for the name as written misses it.

The register ingest's own `tidy` collapses whitespace, so these arrived past it — which is
the whole argument for checking the published file rather than trusting the writer. An
invariant now holds every published file to one space between words.

## A race worth noting

The recovery pass loaded `catalogue.json` at start and wrote it at the end. I fixed the
doubled spaces in that same file while it was running, and the write overwrote my fix. No
harm — the fix is idempotent and was simply re-applied — but two writers on one file is
how a repair silently disappears. Finish one, then start the next.

# Sixth pass — the records nobody could type

All that repair work was in service of records being *findable*, so the next thing to
check was whether search could actually reach them. It could not.

Search compared lowercased strings and nothing else. **1,957 records — one name in ten —
were effectively unreachable**: Bagòss, crème brûlée, aşure, Erdäpfelknödel, niño
envuelto, rødgrød.

This is the same failure as the Cyrillic *с* inside "cheese", from the other side. There
the data held a character nobody would type; here the reader was asked to type one they
cannot reach. Both end with a record that exists and cannot be found. **The reader who
knows a dish well enough to look it up is usually the one least able to type its name.**

`src/domain/fold.ts` drops the marks Unicode can decompose and maps by hand the letters it
cannot — ø, ß, æ, œ, ł, đ, ð, þ, ı — because those are letters in their own right rather
than a base plus a mark, and survive `NFD` untouched.

Two rules that matter more than the mechanism:

- **Both sides, never one.** Folding only the query leaves "creme" missing "crème"
  exactly as before.
- **Latin only.** A Devanagari or Arabic mark is not a decoration on a letter, it is part
  of which letter it is. Folding those would make search answer with a *different word*.
  There is a test asserting कढ़ी, كبسة and 刀削麵 come back unchanged.

Verified in the search box on production rather than only in tests:

| typed | result |
|---|---|
| `hakarl` | 2 matches, Hákarl |
| `rodgrod` | 1 match, Rødgrød |
| `creme brulee` | 3 matches |
| `cordoba` | 2 matches |
| `bogoss` | 0 — the fold has not become a wildcard |

## A note on driving the app to check

`computer type` did not land in the search box — react-native-web's controlled input
ignored the synthetic keystrokes and `input.value` stayed empty while the results list
sat unchanged, which looks exactly like "the feature does not work". Driving it through
React's own value setter and dispatching `input` exercises the same `onChange` path and
does land.

Worth remembering before concluding from a browser check that a feature is broken: **the
harness failing to type is indistinguishable from the app failing to search**, unless the
input's value is read back.

# Seventh pass — search that answers the question asked

Two faults, found by driving the real search box rather than reading the code.

## Word order was load-bearing

The query was matched as one substring, so the reader had to type a record's words in the
order the record happens to store them. Measured on production:

| typed | before | after |
|---|---|---|
| `pizza margherita` | 2 | 2 |
| `margherita pizza` | **0** | 2 |
| `halwa kozhikode` | **0** | 1 |
| `mole oaxacan` | **0** | 1 (Oaxacan Mole Negro) |
| `pizzza` | 0 | 0 |

The query is now a set of terms, each folded, all of which must appear — so it stays a
narrowing search rather than a fuzzy one, while the terms may fall anywhere, in any order,
and across different fields. "naples pizza" takes the place from the breadcrumb and the
name from the title.

## Relevance was not part of the ordering at all

Searching "tomato" returned 411 records ordered by evidence, and all twelve records
actually *named* for a tomato sat at the bottom, because an unscored record scores zero.
The search was answering "the best records that mention tomato" when it was asked
"records about tomato".

A name match now outranks a mere containment, and *within* each group the reader's chosen
sort applies untouched — so the file's existing rule, that authenticity and popularity
never feed each other, still holds. They were not mixed; they were asked a narrower
question first.

Two tiers only. Finer scoring — how early the word appears, how much of the name it covers
— is guesswork dressed as precision, and this atlas has enough numbers that mean something.

## Two ways a browser check can lie, both hit today

1. **The harness could not type.** `computer type` did not reach react-native-web's
   controlled input: `input.value` stayed empty and the results list sat unchanged, which
   is indistinguishable from a broken search. Reading the value back is what caught it.
   Driving through React's own value setter and dispatching `input` works.
2. **The page was running last week's code.** After deploying, the first check said
   nothing had changed. The browser held a cached `index.html` pointing at
   `entry-4ed4ec5a` while the deployment served `entry-419cf44a`. Comparing the bundle
   name in the page against the one the site serves settled it in one call.

Both produce the same symptom — "the change did nothing" — and neither is a fact about the
change. **Check that the page is running the build you think it is before believing a
negative result.**

# Eighth pass — the heading outline, finally verified

The heading roles shipped days ago and were recorded as unverified. Checked in a browser
at last, and two faults were visible immediately.

## Five headings on the home page were not headings

`Stat` used `H6` for its "DISHES", "COUNTRIES", "DOCUMENTED", "REGISTERED", "AUTHENTIC"
labels, purely for the uppercase treatment. Each entered the document outline, so somebody
navigating by heading met five section titles that are not sections — each announcing a
single word with no content beneath it.

H6's own comment already said what it is: *"It is a signpost, not a heading."* And marked
it as one anyway. `Eyebrow` is that signpost — same treatment, no role.

## Levels were inferred from size, and size is not depth

"Most looked up" is a rail on the home page, a sibling of "Disappearing" and
"Authenticated", but it is drawn small — so it announced itself as level 4 straight after
level 2. The record page was shifted the same way throughout: its sections sat at level 3
with nothing at level 2 above them.

Headings now take an optional `level`, so a smaller treatment can keep its real place in
the outline without changing what it looks like. **Where size and depth disagree, the
outline wins.**

| | before | after |
|---|---|---|
| home page headings | 12, five of them phantom | 7, all real |
| home page skips | 2 → 4 | none |
| record page skips | 1 → 3 | none |

## Two more zero-viewport artefacts, correctly ignored

The Browser pane reports `innerWidth: 0`, so `useLayout().wide` is false and the desktop
footer legitimately returns null — `role="contentinfo"` was absent, and it would have been
easy to file that as a missing landmark. It is not: the phone colophon renders in its
place, exactly as designed. Same family as the `requestAnimationFrame` finding earlier:
**a zero-size hidden pane makes several correct behaviours look like faults.** Check the
viewport before believing one.

# Ninth pass — the page was 15 MB, and 9 of it was thumbnails

Ajay asked weeks ago why rendering was slow. The first-paint work cut chrome and deferred
the method text. This is the rest of the answer.

The atlas requested **full-resolution originals** and drew them in a 192px card. On the
live home page: **8.9 MB of photographs for 63 thumbnails**, one of them 1,645 KB alone,
the largest arriving at 2269×1856 to be shown at 192×192.

Commons scales on request. Measured over 22 of the home page's photographs:

| | |
|---|---|
| originals | 19.65 MB |
| at `width=384` | **1.07 MB** |
| saving | **95%** |

Every Wikimedia URL is now normalised to `Special:FilePath/NAME?width=N`, with the width
coming from the call site: a shelf card asks for twice its own card size, the record hero
for 1200, everything else 400.

## The repair that would have broken 5,998 photographs

Three URL shapes, none width-limited: 3,055 `Special:FilePath`, 5,998
`upload.../thumb/...`, 1,585 originals. The obvious fix for the middle group is to edit
the `960px-` in the path down to `384px-`.

**Commons answers HTTP 400 for that.** Every one of those 5,998 would have become a broken
image — and a test that only checked the URL had changed would have passed. Four curl
calls before writing any code is the only reason that is not in the commit.

The file name is recoverable from all three shapes, so all three normalise to the one form
that works rather than each being patched its own way.

## Two smaller honesty notes

- For an original already narrower than the requested width, the re-encode can come back
  *larger* — 2 of the 22 measured. A rounding error against 95%, but it is real and it is
  in the commit message rather than left out of it.
- `encodedBodySize` reads 0 for these now: the request redirects cross-origin and the
  timing data is withheld. The browser could no longer measure what it measured before the
  change, so the after-figure was taken with curl. **When the instrument stops reporting,
  that is not the same as the number being zero.**
