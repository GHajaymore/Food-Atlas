# 2026-09-01 — structured data, and the accounts moved off the critical path

Two pieces of work, both under Ajay's *"keep going, make it world class for a cause"*.
Everything below is committed and deployed to `wikifoodia.ajailabs.app`.

## 1. `schema.org/Recipe` on the prerendered records — `6820504`

4,488 record pages ship Recipe JSON-LD with the real ingredient list, the real method
(28,363 steps) and a `citation` to whoever recorded it. That is what lets a search result
show a photograph and a method rather than a blue link, which for an atlas distributed by
search is most of its reach.

**Only where there is a method.** 3,119 records have ingredients and no method and cannot
promise `recipeInstructions`, so they get no markup rather than a hollow one.

**Nothing invented.** No `cookTime`, `recipeYield`, `nutrition` or `aggregateRating`. Rich
results reward all four and the atlas holds none of them.

The first run marked up **6 records**, because `cookbook.json` ships without its step text
and a build script never runs the second fetch. Nothing failed — the file count was
identical and the run reported success. See the shared fix in §2.

Verified live: present in the served document, parses, the app renders over it, and the
inline block is not rejected under the CSP.

## 2. `prepSummary` deferred — `9d99342`

`cuisines.json` was 1,434 KB of a 2,583 KB critical path, and 46% of it was prose that one
screen reads as prose.

```
critical path   2,583 KB  ->  2,145 KB   (438 KB, 17% less)
```

**17%, not the 26% first estimated** — the card needs the opening 220 characters and the
field averages ~400, so half of it was never going to move. `docs/first-paint.md` has the
full write-up, including the correction to its own earlier claim that this field was
immovable.

New on a record: `prepLength`, alongside `stepCount`. Ask `hasProse()` / `methodLength()`,
**never** `prepSummary.trim()` or `steps.length` — the strings are empty until the second
payload lands.

### The gate is the reusable part

`scripts/verify-prose-split.mjs` builds the catalogue from the old published files and the
new ones and compares every score, badge, blurb and at-risk finding across 17,477 records.
It caught **597 records losing their Wikidata description** on the first run. Run it before
any future change to what `compact-data.mjs` writes:

```
node --experimental-strip-types --import ./scripts/lib/ts-resolve.mjs \
  scripts/verify-prose-split.mjs <dir holding the previous public/data files>
```

### `scripts/lib/built-catalogue.mjs` — read this before writing a build script

Deferring text has now broken a build script twice: recipe markup for 6 records instead of
4,488, then **8,890 prerendered pages falling to 7,607** with the sitemap agreeing with the
wrong number. Both failed silently. Any script that needs a *finished* catalogue calls
`builtCatalogue()`; anything deferred in future belongs in that function.

### Two defects it uncovered

- `documented()` in the dedup ranker read `d.steps.length`, which has been 0 for every
  cookbook record since the step text was deferred — costing them the tie-break against
  thinner imports of the same dish.
- `plumbing.test.ts` traced the `prepSummary` field, which no published row carries any
  more, so its guard would have skipped it in silence.

## Measured and rejected

`langNames` is still immovable — `queries.ts` searches it, `proposals.ts` dedupes against

## 3. The card image was broken on every record — `0aadd3b`

A record stores a Commons *file name*; `sizedPhoto()` rebuilds the URL. Every screen in the
app goes through it and `prerender-records.mjs` did not, so all **5,547** record pages
published `<meta property="og:image" content="Popcorn%209.jpg">`, and 1,712 Recipe blocks
carried the same non-URL as their `image`.

Every link shared into WhatsApp, Slack or a group chat previewed as a title and a blank
square. Nothing failed — the tag was present and non-empty, and the check counting how many
records carried an image counted these as carrying one.

**Also measured: the prerendered article is what a search visitor reads for the first 1.3
seconds.** Sampling `#root` every 16 ms, the record's own HTML stays up from first paint
until the app replaces it at 1,275 ms, and the loading skeleton never renders on a record
page. So the article now carries the photograph and its credit.

Baking the same idea into the front page was built, deployed and reverted the same hour —
on `/` React commits immediately, so it adds a flash before the skeleton instead of
replacing it. Both the finding and the failure are written up in `docs/first-paint.md`.

**If you change `prerender-records.mjs`, read the output.** Every fault in it so far —
6 records marked up instead of 4,488, 8,890 pages falling to 7,607, 5,547 broken card
images — produced a successful run and a wrong file.
